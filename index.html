DeepKDS — POS-independent Kitchen Display System

My role
Architect and lead developer, from an empty repository
Period
Feb 2025 – present
Platforms
Windows, Android, macOS, Linux on Raspberry Pi
Core stack
C++17, Qt/QML, ZeroMQ, RabbitMQ, WebRTC, SQLite

The problem

A kitchen display system normally has to be integrated against each POS vendor's API — which assumes the POS exposes one, or gets redeveloped to. Every deployment is then gated on a third party's cooperation. DeepKDS reads order data from the POS's own printer output instead, so it drops into a restaurant without the POS vendor being involved at all.

What I built

  • POS independence. Co-created the DeepKDS AI Agent, middleware that captures and interprets order data directly from printer output, removing any dependency on POS vendor APIs and making the product compatible with POS systems worldwide.
  • Cross-platform architecture. Architected and developed the product from the ground up in C++/Qt/QML, one codebase serving Windows, Android, macOS and Linux on Raspberry Pi, with ZeroMQ and RabbitMQ carrying real-time, low-latency data between distributed systems.
  • Reliability on restaurant networks. A fault-tolerant messaging layer with dual-broker failover, exponential-backoff reconnection and transaction-level deduplication, so displays keep serving orders through broker outages and the unstable connectivity typical of a working kitchen.
  • Remote support without a site visit. Peer-to-peer remote control and screen sharing on WebRTC, with hardware-accelerated H.264 encoding written per platform (MediaCodec, Media Foundation, V4L2, x264), so support engineers diagnose and fix on-site issues without dispatching a technician.
  • Secure back-end channel. Designed and implemented the protocol between the app and the web server covering device registration, subscription management and remote support sessions.
  • Internationalisation. Ten locales with automatic menu translation, so a single build serves restaurants in different countries instead of maintaining localised forks.
  • Hardware and third-party integration. Serial customer-pager protocols, thermal receipt printers, text-to-speech order announcements, and Kakao AlimTalk for automated customer notifications.
  • On-device persistence. SQLite with write-ahead logging, indexed queries and automated retention policies, holding response times steady on low-power embedded hardware across long-running deployments.
  • Observability. Structured, category-based logging and symbol-resolved crash reporting, so a field failure can be traced to a line of code across very heterogeneous deployment environments.
  • Release engineering. A cross-platform CI/CD pipeline producing signed, self-contained builds for Windows, Android and Raspberry Pi, which shortened release turnaround and removed manual packaging errors.
  • Interface design. A modern, intuitive UI/UX with AI-assisted insights, built to current design standards.

Smart Pharmacy — Self-service Kiosk

My role
Built the product on a kiosk platform I had written for a previous product
Period
2024
Platforms
Windows (MinGW 32-bit) and Android (min SDK 21, target 30)
Core stack
C++11, Qt 5.15.2 / QML, SQLite
Size
565 first-party C++/QML source files, ~121,000 lines

The problem

A pharmacy counter is staffed for the whole opening day, but a large share of what crosses it is an ordinary over-the-counter sale that needs no pharmacist. This kiosk takes those, so the counter is free for the ones that do. Unattended is the hard part: nobody is standing there when a note jams, a card terminal times out, or a release goes wrong, so every one of those has to have an answer built in.

What I built

  • Reused the platform rather than the product. The kiosk shell, payment stack and state-machine framework came from the tablet ordering system I had built before. Retail-pharmacy sale flow, back-end integration and interface are this product's own, which is why a second unattended product could ship in a fraction of the time the first one took.
  • The sale as a state machine. Twenty named states behind one interface — standby, splash, category and item select, option select, a four-step order confirmation, payment-type select, credit processing, split payment, success, failure, cancellation, refund, admin and environment check. Unattended means no one is there to nudge a stuck screen, so every step is somewhere the machine can be, not a branch inside a function.
  • Card payment across the Korean market. Credit payment behind an abstract base and a factory covering four PG vendors (KICC, KIS, NICE, SMARTRO), with a fifth (KOCES) implemented against the same base, and a second layer of the same shape for eight VANs (FDIK, JTNET, KCP, KFTCONE, KICC, KIS, KOVAN, KSNET). A pharmacy keeps whichever provider it already has.
  • Cash, including change. A note and coin unit driven over serial with its own state machine — idle, init, deposit, withdraw, flush, return, and separate abort-return and error-return paths — plus a bill dispenser for change. A machine holding a customer's banknote with nobody nearby has to know exactly which state it is in and how to give the money back.
  • Everything else people tap. Mobile wallets and QR schemes, app card, and the T-money transit card through its vendor SDK.
  • Handoff to the pharmacist. Completed sales are pushed to a kitchen-display-style screen behind the counter with the order, payment and call-number data, so staff see what the machine sold without watching it.
  • Store-driven configuration. Each device pulls its own environment, product catalogue and images from the back-end, with sold-out toggling, display ordering and order-history sync, so a pharmacy is set up from the server rather than at the machine.
  • Updating itself, and being made to. The Android build downloads and installs its own replacement, with a forced-update path for when a version must not stay in the field.
  • Three languages. Korean, English and Japanese throughout the customer-facing flow and the admin screens.
  • Field diagnostics. Per-day rotating log files tagged with the device and pharmacy identity, so a report from one machine can be traced without physical access.
  • An HTTP server inside the kiosk. The machine listens rather than only polls: an embedded HTTP daemon accepts pushed JSON from the store agent, so sold-out changes, receipt-store settings and payment results reach the screen the moment they happen instead of on the next poll.
  • Two toolchains from one tree. One qmake project produces both builds — Qt 5.15.2 MinGW 32-bit for the Windows cabinet and Clang multi-ABI for the Android board — with the platform-specific pieces (serial cash unit on Windows, JNI payment apps on Android) selected at build time rather than forked.

HCMUT · Bachelor thesis · 2021

Teaching-less SCARA Robot

Full title
Development of automatic teaching method using stereo camera for SCARA robot
Programme
B.Eng. Control Engineering & Automation, HCMUT — GPA 8.12/10
Supervisor
Dr. Nguyen Hoang Giap
Robot
EPSON SCARA with its own controller, driven over LAN
Vision
Stereo rig built from two Basler Dart daA1600-60um cameras — 2 MP, 1600×1200 at 45 FPS, USB 3.0, working range 500–1500 mm
Core stack
C++, Qt / QML, OpenCV, MATLAB (analysis tooling)

The problem

Teaching an industrial arm the conventional way means jogging it by hand to every point of a task and storing each pose. It is slow, and the whole thing has to be redone whenever the work changes. Teaching-less replaces that: the camera measures where the object actually is, and the robot is told how far to move. The difficulty is that the camera measures in its own frame while the robot moves in another, and a SCARA also has to arrive with the right end-effector rotation, not just the right position.

What I built

  • A master/slave system across the network. On the master, a PC reads the stereo pair, computes how far the robot has to travel, and encodes that as a message. On the slave, the EPSON controller decodes it back into a displacement and executes the pick-and-place. The two talk over LAN through a socket protocol I defined, using the controller’s own network-server, looping and motion command set.
  • Four concurrent flows. Image processing, position computation and transmission, end-effector rotation tracking, and controller communication each run as their own flow, because the camera cannot stop looking while the robot is moving.
  • Rotation, not just position. A SCARA that arrives at the right coordinate with the wrong wrist angle still misses the part, so the system continuously recomputes and updates the end-effector rotation from the marker rather than assuming it.
  • Tracker and pick-place modules. The operator-facing application splits into a tracker module for the vision side and a pick-place module for the task, behind one interface.
  • Purpose-built test hardware. Comparing candidate marker types before choosing one, then designing and fabricating the camera mount, an acrylic accuracy panel, and its stand — measuring the error needed apparatus that did not exist yet.
  • A second application just for measuring error. Separate tooling for the repeatability and coordinate-comparison experiments, plotting the results rather than reading numbers off a table.

How it was validated

Four experiments: repeatability of the vision system; whether the distance between two points measured by the stereo rig agrees with the same distance measured by the robot controller; how far the coordinate read back after a move differs from the one sent; and whether the arm reaches a commanded setpoint. The last of these was run at four setpoints, checking both position and angle against the starting pose.

What did not work

The marker carried retroreflective points on only three faces, so when the robot rotated an unmarked face toward the camera the system lost the ability to update its rotation angle. Synchronisation between the robot’s motion and the capture instant was also left unoptimised, which limits how fast the loop can run. The thesis proposes a marker with more faces and better motion-capture timing as the next steps.

Mobile Manipulator with Marker-Vision Tracking

Full title
Design mobile manipulator system using Marker-Vision Tracking algorithm
Programme
M.Eng. Control Engineering & Automation, HCMUT — GPA 8.46/10
Supervisor
Dr. Nguyen Hoang Giap
Period
Sep – Dec 2022, defended January 2023
Core stack
ROS on Ubuntu, C++, Python, Qt, OpenCV / ArUco
Hardware
Differential-drive AGV, 5-DOF arm, LiDAR, stereo tracking camera, RGB-D camera, BLDC drives, embedded PC

The problem

An AGV moves goods across a factory, but somebody still has to load it and unload it. Mount an arm on top and that person is no longer needed — which only works if the arm can actually reach the object when the vehicle stops. That is the catch. An AGV navigating on wheel odometry and SLAM parks to roughly nine centimetres, and an arm reaching for a specific box does not have nine centimetres to spare. The vehicle is accurate enough to arrive; it is not accurate enough to arrive somewhere the arm can work from.

What I built

  • Marker-vision tracking for the final approach. Navigation gets the vehicle close; a stereo tracking camera watching a passive marker on the robot closes the last gap, measuring the marker to better than 0.2 mm and correcting the pose before the arm moves. Average parking error dropped from about 9 cm to about 3 cm.
  • The pick station is wherever you put the marker. Because the target is defined by the marker rather than by a taught coordinate, moving the marker moves the station. No re-teaching, no re-surveying a position each time the line changes — the same idea as my bachelor thesis, applied to a vehicle instead of an arm.
  • Grasping by sight, not by memory. An RGB-D camera on the arm finds the ArUco-tagged object in the frame and resolves its position at grasp time, so a small residual error in where the vehicle stopped does not become a missed pick.
  • An end effector that does not drop the payload. Electromagnetic gripper on the final axis paired with a steel-plated tray, so the load stays put while the vehicle is moving rather than only while the arm is holding it.
  • Navigation stack. LiDAR SLAM for mapping, AMCL for localisation, and Dijkstra and A* path planning through move_base, with odometry computed from wheel encoders.
  • Operator interface. A Qt application for driving and monitoring the vehicle.

What did not work

The thesis is explicit about its limits, and they are worth repeating. The 5-DOF arm carried enough mechanical error to dominate the end-to-end pick accuracy — the vision was not the weak link, the mechanics were. The driver for the fifth axis failed partway through and was never replaced, so that axis could not rotate during the recorded experiments. The chassis had no suspension, so on uneven or slippery floors the wheels lost contact and odometry drifted. And the operator interface only ever drove the vehicle, never the arm.

OrderEAT — Tablet Ordering System

My role
Designed and implemented from inception
Period
May 2023 – Aug 2024

Windows (MSVC 2019) and Android (min SDK 21, target 30)
Core stack
C++11, Qt 5.15 / QML, SQLite, AMQP, AWS
Size

The problem

Restaurants in Seoul wanted guests ordering from a tablet at the table rather than queueing at a counter. That one change puts the tablet in the middle of everything the restaurant already runs: it has to agree with the POS, hand tickets to the kitchen display, and take a Korean credit card, all without the guest noticing any of it.

What I built

  • The product, from inception. Designed and implemented OrderEAT for both Windows and Android from an empty repository, in C++11 and Qt/QML, growing to roughly a thousand first-party source files.
  • The order flow as an explicit state machine. Around twenty named states behind a single interface — standby, splash, order-type select, menu select, order review, payment-type select, credit processing, instalment-month select, split payment, success, failure, cancellation, refund, reservation, on-delivery, admin and environment check. Payment is where a kiosk actually breaks, and giving every step a state of its own means a failure has somewhere defined to go instead of leaving a customer staring at a frozen screen.
  • Card payment as a pluggable vendor layer. Credit payment sits behind an abstract base and a factory, with four Korean PG vendors wired through it (KICC, KIS, NICE, SMARTRO) and a fifth (KOCES) implemented against the same base. A separate VAN layer, same shape, covers eight more (FDIK, JTNET, KCP, KFTCONE, KICC, KIS, KOVAN, KSNET). Onboarding a store that uses a different VAN is a new subclass, not a change to the order flow.
  • Everything else Koreans actually pay with. Mobile wallets and QR schemes, app card, and the T-money transit card through its vendor SDK — plus a physical cash and coin acceptor driven over serial, with its own init, deposit, withdraw, flush and abort-return state machine, because a machine holding someone's banknote cannot be allowed to lose track of it.
  • In-restaurant integration. Protocol packet encoders and decoders for three POS families, including table-occupancy lookup so a tablet order attaches to the right table, and handoff to the kitchen display.
  • Messaging. A RabbitMQ layer over AMQP handling exchange and queue declaration, binding, consumption and automatic reconnection, alongside a TCP client and server and an embedded HTTP server for talking to other devices on the store's own network.
  • Cloud sync. Around 180 typed request and result classes against the back-end covering menu and category management, sold-out toggling, display ordering, image registration and per-store environment download.
  • Updating itself. On Android the app downloads and installs its own replacement, so a store's kiosks move to a new build without anyone visiting them.
  • Themeable storefront. Independent QML theme trees let one binary present a completely different interface per brand, with a dedicated sold-out treatment. Views follow MVVM with a C++ view model behind each screen.
  • Serving-robot handoff. Screens for cooking-complete, robot-arrived and robot-departed, plus an employee-call status view, so the kiosk participates in table service rather than stopping at the receipt.
  • Field diagnostics. On-demand screen capture the support side can pull back, for reproducing what a customer saw.
  • Ways of working. Requirements tracked in Notion, designs handed over in Figma, source control on remote Git repositories.

Working with the Korean team

Two on-site assignments in Korea totalling four months, working directly alongside the local team — the start of the three years of Korean collaboration I have now.
